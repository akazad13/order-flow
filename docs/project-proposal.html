Project Proposal: Spec-Driven Event-Driven Order Platform

2026-10-14

Summary

Build OrderFlow, a small event-driven order fulfillment platform, over 8 weeks where every feature starts as a written spec and every spec ends as an automated test. The domain is familiar (place an order, reserve stock, take payment, notify the customer), so the learning effort goes into the method, not the business rules.

Spec-driven development (SDD) here means: the spec is the source of truth, code and tests are derived from it, and a change to behavior starts with a change to the spec. The project exercises four kinds of spec: a feature spec in plain language, Gherkin acceptance criteria, OpenAPI for HTTP, and AsyncAPI for events.

Domain and scope

A customer places an order in a web UI; four services cooperate through events until the order is confirmed or cancelled. No service calls another service's HTTP API during the order flow.

Features (each one is a spec)

  1. Place an order and see it confirmed.
  2. Reject an order when stock is short, with a clear reason.
  3. Cancel the order and release stock when payment fails.
  4. Handle a duplicate event without double-charging or double-reserving.
  5. Show live order status in the UI (polling or SignalR).
  6. Customer cancels a pending order.

Out of scope: real payments, authentication beyond a fake user, multi-currency, deployment to a cloud.

Architecture and tech stack

The Order service runs an orchestrated saga; every service owns its data and writes events through an outbox so a crash cannot lose or duplicate a message.

The UI is the only HTTP caller; everything between services is an event on the broker.

The spec-driven workflow

Every feature passes through the same six steps, and no production code is written before step 4. Use GitHub Spec Kit (specify CLI) or plain Markdown templates with the same file names; the discipline matters more than the tool.

  1. Specify (specs/NNN-feature/spec.md): the problem, user stories, acceptance criteria, edge cases, and explicit non-goals. No technology words.
  2. Clarify: list open questions at the bottom of the spec and resolve each one before planning. An AI assistant is useful here as a reviewer that hunts for ambiguity.
  3. Plan (plan.md): which services change, which events and endpoints are added, data model changes, and the test plan per layer.
  4. Contract (contracts/): update openapi.yaml and asyncapi.yaml, then turn acceptance criteria into .feature files. Lint both contracts; run the scenarios and watch them fail.
  5. Tasks and build (tasks.md): small, ordered tasks, each ending with a test going green. Inner loop is TDD.
  6. Verify and close: all layers green in CI, spec status set to Done, and any learning fed back into the spec template.

Testing strategy

Each layer answers one question, and each scenario in a .feature file is automated at the lowest layer that can prove it. Only the critical customer journeys go all the way to E2E.

Testing async flows without flakiness

  • Never Thread.Sleep. Poll with a timeout (Eventually(...) helper or Playwright's auto-waiting expect).
  • Give every test run its own correlation ID and assert on it, so parallel tests cannot see each other's events.
  • Expose a test-only endpoint or event spy that records published events, so E2E tests can assert "OrderCancelled was published" as well as what the UI shows.
  • Fault injection: a header or config flag makes the fake payment gateway fail, so the unhappy path is testable on demand.
  • Idempotency tests publish the same message twice and assert state changed once.

Quality gates in CI (GitHub Actions or Azure Pipelines): spectral lint on OpenAPI and AsyncAPI, unit + component on every push, contract + integration on every PR, E2E on PR to main with trace and video uploaded on failure.

Milestones and timeline

The plan runs 8 weeks at roughly 6 to 8 hours a week, and each milestone is closed only when its specs are Done and its tests pass in CI.

Week 1 builds a walking skeleton on the in-memory bus so the whole loop exists before any real feature; real RabbitMQ and PostgreSQL arrive only in week 5, once the specs and tests have proven their worth. Each week ends with a 15-minute review: which spec was unclear, and which test caught a real bug.

Success criteria, risks and stretch goals

Done means

  • All 6 feature specs written, clarified and marked Done, each with a linked PR.
  • Every acceptance scenario is automated at some layer; a coverage table in each plan.md says which.
  • Breaking an event field fails the contract tests before anything is deployed.
  • Full suite runs locally with docker compose up plus one test command, under 10 minutes.
  • E2E suite passes 20 consecutive CI runs with no retries.
  • A short retrospective: what SDD changed in how you work, and what you would drop.

Stretch goals

  • Swap RabbitMQ for Azure Service Bus or Kafka and prove the specs and tests did not change.
  • Generate an event catalog site from AsyncAPI (EventCatalog).
  • Add OpenTelemetry tracing and assert on traces in an E2E test.
  • Mutation testing with Stryker.NET to check that tests actually test the spec.
  • Consumer-driven contracts for events with Pact message pacts.
